## 2. 流程缺陷（按严重度）

### 高 H1：critic `request-rewrite` 不会自动重跑 04（断链）
- **触发**：workflow 05 Step 7 `verdict='request-rewrite'` 走 `set_critic_verdict` → stage 回 `04-synthesizing`，调 `set_output_status(stale)` 把指定 output 标 stale；但**没有任何机制**告诉主 agent"立即重跑 04"——只在 next_actions 里写了"说『合成 {slug}』"等用户主动触发。
- **影响**：用户若没说重跑，topic 会卡在 04-synthesizing + stale output 的"假完成"态。dashboard 看不出区别。
- **修法**：critic 写完 verdict 后，主 agent 应直接 re-enter `_shared.md` 的增量重写循环（`list_affected_outputs` 会自动捡到 stale）；workflow 05 Step 7 加一句"verdict='request-rewrite' 时**本对话立即**回 04 重跑"。

### 高 H2：`set_user_todos` 在 03/05 仍被以 list[str] 调用，会把 01/02 写好的结构化字段清零
- **触发**：03-extract Step 4/Step 6（line 340-350、383-413）、05-critic Step 7 都直接 `set_user_todos(slug, [str, str, str])`；而 01/02 Step 6 明确禁止此种写法（"⚠️ 禁止覆写"）。
- **影响**：用户在 thesis_v0/roadmap 阶段精心标注的 `priority/info_tier/addresses` 会在 03 收尾时被纯字符串列表覆盖，K# coverage 闭环失效。
- **修法**：03 Step 4/6 改用 `update_user_todo_status` 增量；新加 todo 走 dict 结构。05 Step 7 已部分用 dict，但仍含 list[str] 残留需统一。

### 高 H3：parent_materials 复用路径在 03 完全缺失
- **触发**：workflow 01 Step 1.5 `set_parent_materials` 登记父级 mat_id；workflow 04 `_shared.md` 通过 `format_findings_for_prompt` 自动捞父级 findings；但**workflow 03 不读 parent_materials**——子 topic 03 处理时只看自己的 unprocessed，父级 mat 不会"借"过来生成 findings。
- **影响**：04 时父级 findings 若父 topic 没自己跑过 03，对应 `findings_{mat_id}.md` 根本不存在，`format_findings_for_prompt` 给的路径会指向不存在的文件。
- **修法**：03 Step 1 加一步"检查 parent_materials 中的 mat_id 是否有对应 findings_*.md，缺则让用户/主 agent 决定是否回父 topic 补 03"。

### ~~中 M1~~ → **低 L5：gap_detector 不留痕（评审修正）**
- **subagent 原报告错读**：把 `feedback_gap_detector_checkpoints` memory 当成"已被破坏多次的证据"，提为中风险。
- **实情**：该 memory 是 2026-05-26 同 session 刚写的（commit b73040f），用来**建立**这条纪律——gap_detector 集成 5 个 workflow 之前根本没人调过，零历史数据，谈不上"已被破坏"。
- **底层观察仍成立**：脚本不阻塞、不留痕、易跳过——但属于**未来可能的设计风险**，不是当前发生的问题。
- **修法**（按需推后）：若日后出现真跳过案例，再补"gap 输出写到 `outputs_state.last_gap_check`（含 stage + ts），让 dashboard 红字暴露"；目前无证据先观察。

### ~~中 M2~~ → **低 L4：03/04/05 即兴 web-search 单位表达不统一（评审修正）**
- **subagent 原报告错读**：以为 03=3 / 04=5 / 05=50 是同一维度比较，得出"05 反而最宽松、逻辑反了"。
- **实情**：三处 scope 单位不同，按知识跨度递增是单调合理梯度：
  | workflow | 上限 | scope | 整轮累计 |

  | 03 | ≤3 query | per 单份资料 | ~30 query (10 份) |
  | 04 | ≤5 query | per 单份产出 | ~55 query (11 份) |
  | 05 | ≤50 hit | per critic 轮（一次性） | ~50 hit ≈ 5-10 query |
- **真问题**：单位混杂（query vs hit/query × query），主 agent 跨 workflow 时易混淆。
- **修法**：`_web_prescan_shared.md` 末尾加一张对照表统一表达，不改逻辑。

### ~~中 M3~~ → **低 L6：03 mineru 失败提示不醒目（评审修正）**

### 中 M4：00 Step 4.5 prescan 与 baseline 的写入顺序矛盾 — **已修 2026-05-26**

### 中 M6：07-drilldown 自动入 manifest 触发 04 大重写 — **已修 2026-05-26**
- **真实问题**：drilldown 有双重身份冲突——
  - `auto_resolve_todos` 读 addresses → 闭环 K# todo（✅ 想要）

- **设计协同**：drilldown auto_resolve 路径不变（todo 仍能闭环），仅断了"误触发 04 重写"的副作用；动摇 thesis 时主 agent 显式标 stale，复用 H1 的 critic-stale reason 重写

## 3. 简化机会

### S1：合并 02 Step 0 prescan 与 01 Step 7 prescan 为同一段
- **当前**：01 Step 7（recency=90，triggered_by=01-prescan）和 02 Step 0（recency=30，02-step0）逻辑几乎相同，只差 recency。

- **简化**：保留 01 Step 7（建库时唯一一次 90 天扫），02 Step 0 改为"仅在 last prescan > 14 天时增量扫"——脚本判断，不让主 agent 决策。

### S2：03 Step 0 "扫 inbox 报错退出" 改为 02 自动 trigger
- **当前**：03 Step 0 检测 inbox 有未登记文件就 `raise SystemExit(1)`，让用户回 02。
- **冗余**：这是一次额外手动来回。02 已有 inbox 处理逻辑。
- **简化**：03 Step 0 检测到未登记文件时**自动调 workflow 02 的 add_material 循环**（已是脚本，不需 LLM），跑完再继续 03 Step 1。

### S3：03 Step 5/Step 6 重复问"要不要立即更新产出"

## 4. 一致性问题

### C1：variant 在脚本签名里有的位置参数有的关键字
- `read_topic(slug, variant)`、`set_stage(slug, stage, variant)`、`set_output_status(slug, output_key, status, variant, version=None)` 顺序不一致；workflow 文档里 03 Step 4 `set_user_todos('{slug}', [...])` 漏传 variant，但 02 Step 6 又传了。
- 建议 variant 全部改 keyword-only。

### C2："addresses 强制" 在不同文档对"空列表"态度不一
- 02 Step 4 说允许 `['background']` 占位。
- 07 Step 4.5 说允许 `addresses: []`（"纯 ad-hoc 问题"）。
- `_web_prescan_shared.md` 关键纪律 3 说"必填，否则 auto_resolve 算不进"。
- 三种"空"的语义需要统一文档约定。

### C3：mineru 默认模型不统一
- 02 Step 4.5 `convert(src, out_dir, 'vlm')` 写死 vlm。
- 03 Step 2.1.B 命令行 `--model vlm` 一致。
- 但 memory `feedback_mineru_required` 说"必须 vlm 不能 pymupdf"，文档里没明确禁止；新人按默认改 mineru 时易跌坑。

### C4：thesis 章节数 v0 是 5 段，v1+ 是 11 段
- v0（00 Step 5.0）：5 段。
- v1+（04 `_shared.md` Scheme C）：11 段。
- 章节编号、强制结构、parent_version 标记都变，跨版本 diff/review 困难。建议 v0 也兼容用 11 段空填（§4 K# 现状表、§7 数据缺口 v0 都能写），统一格式。

### C5：`material_count(slug)` vs `material_count(slug, variant)` 调用混乱
- 04 `_shared.md` 前置检查 `material_count('{slug}')` 不传 variant。
- 03 Step 4/6 `material_count('{slug}', '{variant}')` 传。
- manifest.py 实际签名是两参数必填——前者会 raise。

### C6：critic verdict 后是否要写 thesis_v{N+1} 没有强制
- 05 Step 7 提了一句"若 critic 触发新的 thesis_v{N+1}（无论 verdict 类型）"，但没说什么条件下触发。建议明确：`request-rewrite/request-more` 都要写新 thesis，`approve` 不强制。

## 5. 最强 3 条建议

### 建议 1（ROI 最高）：让 critic verdict 直接驱动后续 workflow，而不是写完 verdict 等用户喊话
当前 `request-rewrite`/`request-more` 之后主 agent 就停手，整轮研究卡在 stale 态。把 verdict 写完后立即接续到对应 workflow（同一对话内），能消掉一半"卡 stage"问题（修 H1 + S4）。

### 建议 2（ROI 高）：把 user_todos 结构化校验 + dashboard 红字告警一次做透
现在 `set_user_todos(list[str])` 在 03/05 仍能调用 → 老 todos 字段被清零（H2）。让 `set_user_todos` 检测到纯字符串入参时 raise，配合 dashboard 把 `addresses 缺失`/`gap 未体检`/`stale output 未重写`三类异常打红——纪律靠脚本而不是文档强制。

### 建议 3（ROI 中高）：合并 prescan / mineru / inbox-scan 这三处"02 自动应做但 03 重复检查"的逻辑
S2 + S1 + M3 实质都是"03 起手做了 02 应该做完的事"。把 03 起手的健康检查全部下沉到 02 收尾时的 invariant 校验（脚本 enforce），03 Step 0 整段可删掉 ~60 行。
